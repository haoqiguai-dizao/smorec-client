# Exact encoded sample duration

The native repair restores each hardware-encoded H.264 sample's original duration before the existing fragmented MP4 sink consumes it. It is enabled whenever the hardware fragmented path is requested; `FRAMEFLOW_CAPTURE_ENCODED_TIMING=0` explicitly disables it for diagnostic comparisons. Software and diagnostic standard MP4 sessions bypass the wrapper. After the controlled comparisons below, the application now prefers hardware and falls back to software when hardware startup fails. `FRAMEFLOW_CAPTURE_ENCODER=software` explicitly selects the software diagnostic baseline.

This targets a demonstrated container boundary issue. Continuous input ending at 10.2342607 seconds produced 445 hardware samples whose fragmented file ended at 9.98155 seconds. Standard MP4 retained the same kind of variable timing to within 0.077 ms. A separate H.264 pass-through probe, with no encoder or capture, produced exactly 10.8 seconds when given accurate durations, but only 10.4 seconds when each duration was nominal 1/60 second. The shortened durations occurred at fragment ends. See [input observations and probe evidence](VIDEO-SAMPLE-DIAGNOSTICS.md).

## Scope and implementation

- `EncodedTimingLedger.h`: 512 fixed metadata entries, storing only PTS, duration and a unique insertion token. The ledger occupies less than 20 KB regardless of recording length. It never stores media samples or pixels.
- `EncodedSampleTiming.{h,cpp}`: actual encoder preflight, synchronized metadata matching, first-failure propagation and final diagnostic summary.
- `EncodedTimingSink.{h,cpp}` and `EncodedTimingStream.h`: thin COM forwarding wrappers around the original media sink and fixed streams. The video stream corrects duration; audio passes through.
- `OutputManager`: delegates its two video writes and writer maintenance points, and validates the final result. The recording loop's maintenance call propagates failure through its existing error path; capture and sample ordering remain unchanged.
- `SinkWriterInitialization.h`: releases failed startup writers before shutting down their sinks, including explicit cleanup before the existing manual NV12 retry. Successful startup dismisses this guard.
- `MediaClockOrigin.h`: read-only presentation-clock/QPC correlation, exposed as `Recorder.GetMediaClockOriginQpc100ns()` without altering existing event signatures or sample timestamps.
- `StaleWriterMaintenance.{h,cpp}`: bounded metadata health checks at the existing periodic maintenance point on confirmed hardware with normal writer backpressure; other paths retain their original flush.

The map is enabled only after `IMFSinkWriterEx::GetTransformForStream` identifies the selected video encoder and its attributes contain a nonempty `MFT_ENUM_HARDWARE_URL_Attribute`. Merely requesting hardware is insufficient: Media Foundation can choose a software transform, whose resampling would invalidate exact PTS matching. An unconfirmed transform fails preflight before `BeginWriting`; the helper's existing startup fallback can then recreate software recording at the requested resolution. The log records a reason and HRESULT, and the hardware encoder's friendly name when available.

Source PTS/duration metadata is inserted immediately before the existing `WriteSample`, allowing synchronous output to match. Encoded `ProcessSample` requires an exact PTS match, sets only `SampleDuration`, and immediately forwards the same sample. It does not modify PTS, DTS, payload, flags, sample count, fragment policy, scheduling, encoder settings or queue backpressure. No lookahead or sample buffering is introduced.

## Lifetime and failures

Source writes and the existing writer flush calls are serialized by the current recording task. Encoded output can be asynchronous. Short mutex scopes protect the metadata and counters; no COM call executes while that mutex is held. The sink owns its stream wrappers; stream reference counts retain the parent without an ownership cycle.

Both native MP4 sink variants on the test host report characteristics `0x4` and do not declare fixed streams, even when constructed with a complete output type. The wrapper snapshots those existing streams and itself declares a fixed stream set; Add/Remove explicitly return `MF_E_STREAMSINKS_FIXED`. Initialization does not require the original sink to declare that flag. A no-encoding probe verified one video stream, successful shutdown, a valid byte stream afterward, and sink recreation on that same stream (`output/encoded-sample-timing/sink-characteristics.txt`).

Device-reset flushing and finalization retain their original semantics. Periodic maintenance follows the hardware health-check policy described below; any selected original `IMFSinkWriter::Flush` still executes exactly once. A helper records a token watermark before the call and, only after original success, counts and removes still-pending metadata at or before that watermark. Entries created after that boundary are not removed by the writer helper. An original successful stream-level `Flush` also clears its pending metadata; clearing an already-empty map does not double count. This honors the project's serialized source/flush contract; it is not a claim that arbitrary concurrent source writes and stream flushes are supported. An unexpected late output PTS after a completed flush fails explicitly.

Invalid, duplicate or backward input PTS, missing durations, unknown encoded PTS and capacity exhaustion latch a diagnostic failure. There is no nearest-timestamp match, guessed duration or silent eviction. A failed original write cancels only its own unconsumed insertion. The existing output file and completed fragments are preserved on failure.

At finalization, remaining metadata is an error unless the original flush already explicitly discarded it. The original sink's `BeginFinalize`/`EndFinalize` failures are latched. The writer callback atomically stores its own `OnFinalize(hrStatus)` before signaling completion; OutputManager reads that status after waiting. A later successful `Shutdown` cannot overwrite an earlier failure. These final-result propagation fixes also apply when the optional duration repair is disabled.

The helper must align its stopwatch to the native media clock, rather than estimating the origin as first callback minus one nominal frame. In a static scene the first sample can represent a full second, so that estimate shifts the origin. `GetMediaClockOriginQpc100ns()` queries `IMFPresentationClock::GetCorrelatedTime` and returns system QPC time minus presentation time; both are in 100 ns units. It is an absolute performance-counter time, not UTC. Null, uninitialized, paused, stopped, failed and non-1x clocks return -1. Read and retain the first valid running origin; querying again after a pause produces a mapping including that pause. No clock start/stop, playback rate or sample metadata is modified by this API.

`Recorder.GetCurrentVideoFrameEnd100ns()` exposes the current submitted frame's media endpoint directly from `TimelineManager.GetNextVideoFrameStartPosition()`. Read it only inside the existing synchronous `OnFrameRecorded` callback, before the recording loop advances to another frame; it is not a general cross-thread polling API. Missing native state returns -1. The helper can use origin plus this endpoint for `LastFrameAt`, and separately retain callback delivery time for diagnostics. This avoids including WriteSample/encoder backpressure in the picture's duration. It never infers the endpoint from an output file or changes the tail tolerance.

## Diagnostics and verification

`[EncodedTiming]` logs preflight, the first failure if any, and one final summary. Fields include `registered`, `accepted`, `matched`, `discardedByOriginalFlush`, `cancelled`, `pending`, `highWater`, `writerFlushes`, `finalize` and `timing`. There is no per-frame logging. Together with `FRAMEFLOW_CAPTURE_SAMPLE_DIAGNOSTICS=1`, these permit comparing accepted input count/end, matched encoded count, and independently parsed MP4 sample timing. Accepted input alone does not prove the original queue retained it.

```powershell
# No capture, device access or video encoding.
./native/scripts/test-encoded-timing-ledger.ps1

# Full source rebuild is mandatory; do not reuse native objects.
./native/scripts/build-recorder-fork.ps1
npm run native:build
```

On 2026-09-08, the pure ledger test passed 40,541 assertions, including a 10,000-iteration reuse sequence, exact reordered matching, bounds/overflow, token cancellation and writer flush watermarks. Tests using the real timing state and writer callback also passed for asynchronous finalization errors, first failure retention, stream/writer flush errors and callback event/result propagation. These tests do not simulate a full Media Foundation encoder or establish driver compatibility.

A separate Media Foundation clock test passed without media capture: the reported origin lies between QPC measurements around the real Start call, remains stable after 25 ms, and returns -1 before start or after pause/stop. Correlation arithmetic and invalid values are also covered.

The complete 35-source vendor build and native helper build passed. The first controlled 4K60 hardware run with this repair, synthetic 1080p camera and effects passed (`output/recording-090-hardware-timing-v2/`). Its actual encoder passed the hardware-URL attribute preflight, but supplied no friendly name; no specific GPU encoder model is inferred from that log. All 473 accepted inputs matched encoded output, no pending metadata or flush discards remained, and map high-water was 51 entries. Independent metadata-only parsing found 473 MP4 samples in 32 fragments, timescale 60,000, and actual end 10.26235 seconds versus source end 10.2622915 seconds: +0.0585 ms. All inspected first/last sample duration errors were below 0.0075 ms. Fragment-ending durations now vary rather than all using the nominal 1/60 second. The parsing script is `output/encoded-sample-timing/inspect_fragment_timing.py`; it seeks past media payload without decoding.

The corrected measurement on this controlled scene reported 1.056 CPU cores with preview visible and 0.596 hidden, compared with software's 5.340 and 4.820. Source callback P95 was 18.2 ms versus 18.1 ms idle. These are finite synthetic-window process/scheduling measurements, not a measurement of UU remote mouse latency or proof that every desktop configuration is smooth. The subsequent static, sparse, long-running and crash comparisons are described below; packaged UI/export acceptance remains a separate check.

The fourth ordered patch is `native/vendor/frameflow-encoded-timing.patch`, after exclusion, software encoder tuning and sample observation. All four replay to current sources using an isolated Git index; evidence is `output/encoded-sample-timing/patch-replay.txt`. The latest project has 36 native translation units, including the separate stale-maintenance diagnostic. Every new module is below 450 lines. See [binary provenance](vendor/README.md) for the latest complete build.

Release enablement requires controlled 4K hardware dynamic, static and sparse scenes; exact input/output timing; no missing matches; bounded three-minute memory; original fragment crash recovery; editor/export verification; and a default-off software regression. Use only dedicated synthetic test content, serialize heavy runs, and compare actual desktop/source responsiveness separately from smooth video playback. Test results should name the actual confirmed encoder and driver; success on one GPU is not a universal latency guarantee.

## Controlled stale-flush comparison

The first 181-second static 4K recording reached the existing maintenance branch at 100 rendered frames (`output/recording-090-hardware-static-long/`). It accepted 177 continuous input samples but matched/wrote only 176; `writerFlushes=1` and `discardedByOriginalFlush=1`. Input ended at 181.0386317 seconds, while raw fragmented MP4 ended at 180.03785 seconds: one 1.0007817-second sample was lost. The fixed-tolerance recording verification correctly failed. This is direct evidence of the original queue flush dropping a long static sample, separate from the duration-metadata and callback-clock issues.

The comparison initially required `FRAMEFLOW_CAPTURE_STALE_MAINTENANCE=observe`. Following the successful static, animated and crash checks, this is now the default only when actual hardware timing is active and normal sink writer throttling is enabled. Explicit `FRAMEFLOW_CAPTURE_STALE_MAINTENANCE=flush` restores the original maintenance for diagnostics; software, disabled timing and disabled throttling also retain the original flush. Missing or unrecognized values follow the default. Device-reset flushing and Stop/Finalize remain unchanged. The health branch performs no COM drain operation and retains no payload; existing WriteSample blocking backpressure, strict matching and the 512-entry limit remain intact. It logs `staleMaintenance=observe` and increments `observedStaleChecks`. A latched failure now returns its HRESULT immediately through OutputManager and the recording loop's existing failure path, rather than waiting for another frame or finalization.

The 512-entry limit bounds this module's metadata, not every internal MFT allocation. The controlled test independently monitors the owned native process's private memory and stops with failure above its fixed limit or when memory measurements are missing. The first comparisons used 1 GiB; the dynamic comparison described below uses 3 GiB after checking existing dynamic baselines. This approximate one-second test monitor is not advertised as a production memory bound. The default was changed only after both comparisons retained all samples and showed bounded memory over the test duration. Tests cover default/legacy selection, rejection of unconfirmed hardware, preserved sticky failures, and immediate maintenance-helper error propagation without entering Flush.

The guarded static comparison passed (`output/recording-090-static-observe-long/`): all 176 accepted inputs matched all 176 decoded frames, `pending=0`, `discardedByOriginalFlush=0`, `highWater=2` and `observedStaleChecks=1`. Independent MP4 metadata parsing found 176 fragments and 181.03665 seconds, versus input 181.036678 seconds, a -0.028 ms difference. The helper's separately observed static tail was 0.4254393 seconds with no unresolved timing difference. Native private memory in the visible phase went from about 292 MB to a 485 MB peak and ended at 339 MB; hidden phase started at 339 MB, peaked at 374 MB and ended at 341 MB. The 1 GiB guard was not triggered. This finite comparison validates the exercised static maintenance point; animated pressure and longer-run compatibility remain separate checks.

The first animated comparison (`output/recording-090-animated-observe-long/`) correctly stopped at its 1 GiB test limit, about 1.1 seconds into recording, with 1,621,118,976 native private bytes. All 50 accepted samples matched output, pending was zero and high-water was 24. `observedStaleChecks=0`: the experimental maintenance branch had not executed. Existing dynamic short tests with the original maintenance policy had already peaked at 2,463,834,112 bytes on hardware and 2,211,295,232 bytes on software. The early peak therefore does not establish a leak caused by skipping maintenance. The original failed result is retained.

The separate three-minute animated run (`output/recording-090-animated-observe-budget3-long/`) passed with a fixed 3 GiB guard calibrated against those measured baselines. All 8,742 registered/accepted samples matched all 8,742 decoded frames, with pending/discards zero and high-water 56/512. Independent parsing found 561 fragments, input endpoint 180.6923641 seconds and file endpoint 180.6923666667 seconds: +0.00257 ms. The raw file exceeded the helper's stop-request elapsed time by 2.985 ms during final drain, with no tail hold; that separate comparison is not input-to-container drift. Native private memory peaked at 2,533,412,864 bytes visible and 2,600,751,104 hidden, ending at 2,230,304,768 and 2,062,295,040 respectively without triggering the guard. Combined process CPU was about 1.012 cores visible and 0.621 hidden; source callback P95 was 18.3/18.2 ms with no gaps above 50 ms. These measurements establish a bounded plateau for this run, not a universal production memory ceiling.

The owned-process crash comparison (`output/crash-090-hardware-observe/`) also passed: after forced termination, the existing fragmented prefix decoded to 387 frames and 8.483333 seconds; automatic recovery produced a playable project after restart. Original media and recovery-journal SHA values were retained. This verifies recovery of completed fragments, not preservation of samples that had not yet been written.

The current asynchronous input path allocates a texture copy for each submitted frame. One 3840-by-2160 RGBA texture is 31.64 MiB before allocation overhead; 51 simultaneously retained textures would occupy about 1.58 GiB. Converted NV12 surfaces, encoder buffers, render surfaces and driver allocations can add to this. These sizes make the observed dynamic peak plausible, but they do not identify the actual owners of process private memory. A separate memory-reduction task should first correlate writer statistics and in-flight samples with the measured process curve. Removing the copy or reusing its texture immediately after WriteSample returns would violate the existing asynchronous lifetime requirement.

`NotifyEndOfSegment` only sends an end marker. `PlaceMarker` can confirm when the sink has processed earlier samples, but is not a general encoder memory bound. Directly draining the MFT owned by SinkWriter would require managing output events, restart-of-stream and discontinuity semantics; this experiment deliberately does not introduce that protocol.
