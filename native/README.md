# FrameFlow Windows capture helper

## Dynamic recording exclusions (0.9.80)

`{"id":13,"command":"recording-exclusions","excludedApplications":["C:\\Fixtures\\Helper.exe"]}` updates the active recording; `[]` clears third-party exclusions. Startup and every update resolve the selected application windows and merge only trusted original own-window handles. The active recorder applies the filter on its capture thread and acknowledges after a matching configuration frame. Failed updates restore the previous list; rollback failure saves existing media and reports failure. Input focus and cursor filtering change only after the video filter succeeds. The writer, sound tracks, source origin and recording remain continuous. Window recording rejects excluding its own source application. macOS uses the existing stream content-filter update; it was not compiled in this Windows task. See recording exclusions（内部历史资料未纳入本快照）.

## Windows whiteboard modes (0.9.79)

The Electron parent sends `whiteboard-presentation` with a decimal-string `windowId` and boolean `visible`. The active recording validates the HWND against `FRAMEFLOW_PARENT_PID`; renderer-selected foreign windows are rejected. Pure canvas uses the event journal and protects its local window from screen capture. Complete interface starts a private `--whiteboard-track` child of the recording helper: one WGC window encoder per process prevents ScreenRecorderLib's process-global window engine from corrupting simultaneous window captures. No physical audio is opened by the board helper. stdin EOF or the owning session's stop command finalizes the track; only that owned child can be terminated on a bounded stop timeout.

Both helpers correlate their video origins through the same QPC clock. The child writes `whiteboard-capture.mp4`, identity crop events, offset metadata and separate `whiteboard-capture.log`. Before project loading, Electron stream-copies the fragmented track into seekable `whiteboard.mp4`, with no re-encoding; raw capture remains for recovery. Layout events gate the continuous track across hiding and mode cuts. Version 7 projects keep the authoritative `whiteboard.separateCanvas` flag so demo playback also renders pure canvas without duplicated embedded UI. Existing projects retain their earlier capture semantics. See whiteboard documentation（内部历史资料未纳入本快照） and actual acceptance（内部历史资料未纳入本快照）.

Native recording is real Windows Graphics Capture, encoded incrementally by Media Foundation to H.264 MP4. The screen never contains the Windows cursor: cursor position and clicks are a separate editable track. No browser or mock recording fallback is used.

## Build and requirements

```powershell
# First checkout: prepare the local Microsoft C++ toolchain and build the pinned fork.
./native/scripts/fetch-recorder-fork.ps1
python native/tools/bootstrap_toolchain.py
./native/scripts/build-recorder-fork.ps1
dotnet publish native/FrameFlow.Capture/FrameFlow.Capture.csproj -c Release -r win-x64 --self-contained true -o native/publish
```

Development requires .NET SDK 8. The published x64 helper includes the .NET runtime. Target machines need Windows 10 version 2004 or newer, the Microsoft Visual C++ 2015–2022 x64 Redistributable, a graphics driver supporting Windows Graphics Capture, and Media Foundation (Windows N/KN requires the Media Feature Pack). The default prefers hardware H.264 encoding at the source/selection's native dimensions, rounded down to even pixels. Optional `2160p`, `1440p`, and `1080p` policies cap the long edge at 3840, 2560, and 1920 without upscaling. See [capture specifications](CAPTURE-SPECIFICATION.md) for validation limits and performance acceptance. Unavailable audio inputs produce a warning and do not discard the video.

Hardware startup has a 10-second first-frame timeout and falls back to software if it fails, preserving the requested resolution. Software has a 20-second timeout; `FRAMEFLOW_CAPTURE_ENCODER=software` selects it explicitly for diagnostics. The earlier hardware timing discrepancy was traced through input observations and container experiments to encoded durations at fragment boundaries; confirmed hardware output now restores exact durations before muxing. Normal hardware backpressure also retains pending samples at periodic maintenance points, avoiding the separately demonstrated static-frame loss from Flush. Static/animated three-minute and crash-recovery comparisons passed before the default changed. See [exact timing and validation](ENCODED-SAMPLE-TIMING.md). For controlled diagnostics only, `FRAMEFLOW_CAPTURE_MAX_EDGE` overrides the selected resolution policy (integer 640–8192; invalid values are rejected). Selecting a resolution or encoder is not proof of sustained frame rate, desktop responsiveness, or driver compatibility.

Dependencies are pinned to a local ScreenRecorderLib 7.0.1 fork and NAudio.Wasapi 2.3.0. The fork adds display-session HWND exclusion and separate, verified CodecAPI tuning for the software video encoder; capture clocks and audio/mouse thread priorities remain unchanged. `FRAMEFLOW_CAPTURE_ENCODER_TUNING=baseline` preserves original codec values for diagnostics. `FRAMEFLOW_CAPTURE_ENCODER_THREADS=auto|0..16` overrides video encoder workers only; unset uses two workers, while explicit `auto` requests the codec's automatic selection. See [fork notes](vendor/README.md), [encoder tuning](vendor/ENCODER-TUNING.md), [ScreenRecorderLib](https://github.com/sskodje/ScreenRecorderLib), and [NAudio](https://github.com/naudio/NAudio). Both libraries use the MIT license; preserve their license notices in a release.

## Integration protocol

Launch `native/publish/FrameFlow.Capture.exe` with hidden console and redirected UTF-8 stdin/stdout. Set `FRAMEFLOW_PARENT_PID` to Electron's main-process PID so the app's own windows are excluded from source selection. In ordinary mode, pass visible HUD/webcam HWNDs as `start.options.excludeWindowHandles`, an array of decimal strings. Reuse those windows until recording stops. Ordinary controls use session exclusion rather than global content protection, which also affects remote capture. The opt-in demo mode（内部历史资料未纳入本快照） intentionally omits own-window exclusions on Windows and temporarily changes their content protection, restoring original values on exit.

One JSON object per line. `id` is echoed unchanged. stdout contains protocol JSON only; diagnostics go to stderr.

```json
{"id":1,"command":"sources"}
{"id":2,"command":"start","directory":"D:\\Recordings\\new-empty-project","options":{"sourceId":"window:123456","fps":30,"resolution":"native","systemAudio":true,"microphone":false}}
{"id":3,"command":"stop"}
```

Microphone selection and recording-time mute controls use the same transport:

```json
{"id":4,"command":"microphone-devices"}
{"id":5,"command":"audio-mute","options":{"microphoneMuted":true}}
{"id":6,"command":"audio-mute","options":{"microphoneMuted":false,"systemAudioMuted":true}}
```

- `sources` returns `CaptureSource[]`. Screen IDs are `screen:<Win32 device name>` and window IDs are `window:<decimal HWND>`. `bounds:{x,y,width,height}` uses physical desktop pixels, including negative coordinates. Screen names, sizes, and window titles come from the live OS. Minimized, closed, tiny, and own-process windows are omitted.
- `start.options.excludeWindowHandles` affects only WGC display/region recording. Requested HWNDs must be valid at startup. The fork resolves each HWND through Windows' `GetWindowIdFromWindow`, calls `IDisplayGraphicsCaptureSession.SetWindowExclusionList` before capture, and rejects frames older than the returned configuration iteration. No global window affinity is changed. Availability is checked at runtime, including the actual session interface; unsupported Windows versions fail explicitly and must offer window recording. Window-source capture does not need the list because independently owned HUD/webcam windows are outside that source.
- `microphone-devices` returns active WASAPI capture endpoints as `[{id,name,isDefault}]`; `id` is the original Windows `MMDevice.ID`, and `isDefault` reflects the multimedia-role input. No capture device is started by enumeration. Pass that ID as `start.options.microphoneDeviceId`; omit it or use an empty value to follow the current default. An explicitly selected missing/disconnected endpoint fails startup before any capture begins, with no silent fallback. Failure to open an explicitly selected device is also fatal to startup; ordinary default-input failures retain the existing warning/video-preservation behavior.
- `audio-mute` accepts partial boolean updates `microphoneMuted` and/or `systemAudioMuted` and returns the full `{microphoneMuted,systemAudioMuted}` state. True means muted; an omitted field stays unchanged. It only operates on active tracks enabled by the original `start` options, and rejects disabled/failed tracks or a missing/stopping session. Both requested updates are validated before either is applied. Muting replaces the PCM payload with zeroes at the existing packet position; no samples are removed, no WASAPI client is stopped, and the OS microphone/system volume is unaffected. Command timing is logged under `audio-mute`; the control takes effect at capture-packet granularity.
- `start` accepts `RecordingOptions` from `shared/types.ts`; directory must be empty. `crop`, when supplied, is a source-relative rectangle in **physical pixels**, not CSS pixels or global monitor coordinates. The crop/source keeps its native size by default; optional resolution presets scale down proportionally. Output dimensions are rounded down to even pixels for H.264, with a minimum of 2. Only after the first real video frame, the response is `{"id":2,"ok":true,"data":{"startedAtUnixMs":1788734641378.868,"warnings":[]}}`.
- `stop` waits for encoder finalization and returns `NativeRecordingResult`. `width`/`height` are the actual encoded dimensions. `duration` is the presentation duration, `videoDuration` is the unchanged encoded MP4 duration, and `tailHold` is a verified final-frame hold (zero when none is needed). `directory` is absolute; all media properties are filenames inside it: `screen.mp4`, `cursor.json`, optional `system.wav` and `microphone.wav`. `startedAtUnixMs` estimates video time zero in UTC milliseconds for synchronizing a separately captured webcam; `warnings` reports omitted audio, compatibility fallback, or a detected video clock discrepancy. Disabled/unusable tracks are omitted from the result rather than presented as valid silent recordings.
- Failures return `{"id":3,"ok":false,"error":"..."}` with a diagnostic-log path. Audio failures emit a state event carrying `warning` while preserving video. Fatal video/cursor errors release and flush capture resources before emitting `{"event":"state","state":{"status":"error","error":"..."}}`. A ready recorder emits the same event with `status:"recording"`, `startedAtUnixMs`, and `warnings`. The parent should close stdin and allow graceful finalization before killing a helper.
- Closing stdin gracefully stops and finalizes an active recording; `recording.json` preserves its result even if the parent has exited. A subsequent process cannot resume an in-progress encoder.

### macOS demo filter commands

The ScreenCaptureKit helper accepts optional main-process-owned `captureOwnApp` and `ownAppVisible` booleans in `start` / `live-start` options. Defaults exclude the parent application. Opt-in demo requires a display/region source; a single-window source is rejected. `recording-demo` and `live-demo` accept `{visible:boolean}` and update the active stream's content filter without restarting capture. `recording-demo` returns `{time:number}` on the source media clock for the Electron demo journal. `live-demo` clears the latest-frame buffer before confirming the update. The ordinary whiteboard window exception and other applications' exclusions remain in the filter. These commands are macOS-specific; Windows presentation control is managed by Electron.

### Microphone trial and post-recording effects (0.8.0)

The audio-only trial uses the same native WASAPI endpoint selection, `AudioTrack`, and packet planner as a full recording. It does not start screen, system-audio, cursor, or camera capture. The desktop UI starts it explicitly from **试录 10 秒**, allows early completion, then offers original/effect A/B playback of the same sample.

```json
{"id":7,"command":"microphone-trial-start","directory":"D:\\Recordings\\trial-empty-directory","deviceId":""}
{"id":8,"command":"microphone-trial-stop"}
```

`deviceId` is a native `MMDevice.ID`; empty follows the system default. Start returns `{ready:true}` after the first valid audio packet and rejects an existing recording/trial. `MicrophoneTrial` automatically stops approximately 10 seconds after becoming ready. Stop retrieves the finalized `{duration,file}` result and releases the trial; `file` is the absolute `microphone.wav` path inside the trial directory. stdin EOF also disposes a remaining trial. Trial failure is reported explicitly; the trial is not a recoverable full project.

Electron creates the temporary directory itself and sends only its own trusted path to this protocol. It exposes an opaque trial ID and media capability URL to the renderer, never a renderer-supplied filesystem path. Changing devices, closing the microphone panel, starting a full recording, or quitting ends playback/trial work and releases the endpoint. Original trial files are cleaned up when the trial is discarded. Full recordings keep their independent original microphone WAV.

Effects run in the Electron FFmpeg service after trial capture or during editor/export preparation, not in WASAPI callbacks. The four presets are original, natural speech, clear explanation, and warm podcast; new device defaults use natural speech with automatic volume enabled and a 12 dB maximum boost. Device settings are remembered separately from project effects, and older projects without effect parameters remain unprocessed. The chain includes high-pass, tracked noise reduction, EQ, RMS-based automatic volume, compression, de-essing, downward expansion, and limiting. Preview, trial playback and export share one full-source PCM float32 cache with compensated filter delay and exact sample count; the raw WAV is unchanged. Preparing audio is cancellable, worker threads are limited, and pending preview/trial processing is cancelled before capture. See microphone processing and synthetic evidence（内部历史资料未纳入本快照） for actual parameters and limits.

Camera controls remain outside the native capture helper. Version 0.8.0 places picture settings next to the unique desktop camera preview within its existing HWND, so opening controls does not invalidate the session exclusion list. Display-sized preview processing reduces UI cost without changing raw camera recording or export quality; it does not switch the native screen encoder or establish whole-machine performance. See device interactions（内部历史资料未纳入本快照） and preview performance（内部历史资料未纳入本快照）. Package and full workflow status belong to 0.8.0 acceptance（内部历史资料未纳入本快照）; the protocol description is not a physical-device acceptance claim.

## Real-time live capture and virtual camera

`npm run native:build` publishes the .NET capture helper, then builds the independent x64 DirectShow virtual camera with the local Microsoft toolchain. `npm run native:capture:build` only publishes the capture helper, while `npm run virtual-camera:build` only builds and runs the camera's non-registering DirectShow self-test. Packaged resources include `virtual-camera/XiaoLu.CameraBridge.exe` and `virtual-camera/XiaoLu.VirtualCamera.dll`; no build libraries, SDK or compiler are distributed. See [native camera contract](virtual-camera/README.md) and live feature documentation（内部历史资料未纳入本快照）.

The capture helper adds an independent session whose lifecycle is mutually exclusive with normal recording and microphone trial:

```json
{"id":10,"command":"live-start","pipeName":"xiaolu-live-00000000-0000-4000-8000-000000000000","options":{"sourceId":"window:123456","fps":30,"resolution":"1080p","systemAudio":false,"microphone":false,"excludeWindowHandles":[]}}
{"id":11,"command":"live-stop"}
```

`live-start` returns actual capture `{width,height}` after the first frame. It uses the source's aspect ratio capped at a 1920-pixel long edge, with the selected physical crop and the same session window exclusions as recording. The fifth pinned capture-fork patch adds `RecorderMode.Preview`: capture/clock/bitmap callbacks run at the requested cadence, without creating a video sink writer or recording media. `Stream.Null` only satisfies the managed method signature; it is not encoded-video output discarded after processing. Virtual-camera sessions disable audio. Direct streaming explicitly sets `options.liveAudio: true` and captures the selected `systemAudio` / `microphone` sources without creating recording files. See direct streaming and current validation limits（内部历史资料未纳入本快照）.

### Application exclusion for screen live mode

`{"id":12,"command":"live-applications"}` performs read-only process/window enumeration and returns `[{id,name,executable}]`. `id` is the normalized local absolute EXE path obtained with `QueryFullProcessImageName` using query-limited access; `name` uses the executable's `FileDescription` with a basename fallback; `executable` is the EXE basename. Candidates must own at least one visible top-level window. The helper and its Electron parent PID are excluded. Window titles are never used. Processes whose executable identity cannot be read are omitted rather than guessed from their captions or names.

For `live-start.options.excludedApplications`, omitted keeps the legacy defaults for the exact basenames `直播伴侣.exe` and `xhs-live-helper.exe`; an explicit `[]` disables all third-party exclusions; a nonempty array selects only those exact full EXE paths, compared case-insensitively. At most 32 paths of at most 1024 characters are accepted. Paths must be local-drive absolute `.exe` paths; UNC, device namespace, relative, wildcard, alternate-stream and control-character paths are rejected. A valid saved path with no running matching process is allowed and contributes no windows.

Screen/region capture applies application exclusion. At startup the helper gathers all existing top-level windows of each selected executable, including created but hidden windows, and merges their HWNDs with the trusted own-control exclusion list before `SourceCatalog.Select`. The same merged options reach input monitoring so interaction with excluded windows does not move the broadcast camera. Selection is limited to 32 applications; one application's many HWNDs are retained without truncation. Requested own HWNDs retain strict validation, and unsupported Windows session-exclusion support still fails explicitly. Window-source capture rejects excluding the selected source's application. Ordinary recording also supports application exclusions, with dynamic updates since 0.9.80 as described above.

Each resolution is a window snapshot. During live output, live-exclusions accepts new IDs or refreshes the same selection, keeps the frame pipe, and replaces the capture producer with rollback on failure. During recording, recording-exclusions updates the existing recorder instead. Refresh after new applications, popups or recreated windows. Window visibility and global capture affinity are never changed. Third-party HWNDs are rechecked for validity and process ownership. If a known handle-related startup failure coincides with a lost third-party HWND, one retry removes expired snapshot entries after disposing the failed session; invalid own handles, cancellation, unsupported systems, timeouts and unrelated capture errors are not retried. Cleanup attempts every input, pipe and recorder release even if an earlier release fails; cleanup errors retain the original startup error and prevent a retry. Initial failures return through `live-start`; active failures continue to emit `live-error`.

Run `dotnet run --project native/FrameFlow.Capture.Tests -c Release -- --live-exclusions` for pure synthetic selection, validation, snapshot and startup-cleanup tests. These checks do not enumerate the desktop, create windows, capture media, register a camera, or activate global input.

The main process supplies a fresh `xiaolu-live-<UUID>` pipe name. A current-user-only duplex named pipe accepts one request byte `1` for each latest BGRA frame, then returns a 24-byte little-endian header (magic `0x584c4652`, width, height, byte length, and float64 monotonic timeline seconds) followed by top-down BGRA8. The frame server owns one latest buffer and one transmission buffer; consumers request sequentially instead of queueing stale frames. stdout remains JSON Lines and sends `live-input` events with `{data:[{cursor?},{activity?}]}` plus explicit `live-error` events on failure. Input uses the same Raw Input, caret/UI Automation geometry and reset rules as recording; it never stores typed contents.

With `liveAudio: true` only, each BGRA response has an additional 16-byte little-endian header: uint32 magic `0x584c4155`, uint32 PCM byte length, float64 timestamp of its first sample. The payload is interleaved stereo float32 at 48 kHz, at most 24000 sample frames (192000 bytes); a zero-length packet still carries the header. Timeline and samples share the native capture clock. Both disabled sources produce silence; dual sources have 0.5 gain per track and final peak clipping. Windows uses WASAPI, macOS 15+ uses ScreenCaptureKit `.audio` / `.microphone` output and a same-user Unix socket. Old no-audio clients receive the original video-only protocol. The Electron client validates length, timestamps and fragmented delivery before forwarding PCM to the bounded streaming buffer.

Electron coordinates preview-frame requests, camera composition and a separate BGRA producer process. It exposes only session-scoped live IDs to the renderer, validates lengths and dimensions, and enforces backpressure. The independent DirectShow DLL reads the final composition through a bounded shared-memory channel. Actual desktop/UI scale is unchanged. Closing the helper's stdin stops its live session and releases capture/input/pipe resources; a closed or stale output channel produces black rather than a permanent last private screen.

The device requires explicit user-approved installation and UAC, uses its own name and CLSID, and is not registered by normal startup, builds or tests. This implementation includes x64 receiver support; x86 and actual Douyin/Xiaohongshu platform acceptance remain unverified. Existing record-to-file protocol and original-media recovery remain separate from this live transport.
## Coordinates and timing

The process is Per-Monitor V2 DPI aware. Monitor positions may be negative. Window bounds are read from DWM for every cursor sample so moving a window keeps coordinates aligned. A full-window resize is mapped into the original recording output dimensions; crops stay source-relative. Minimized/closed windows suppress cursor visibility.

The cursor journal samples approximately 60 times per second, with a dedicated low-level mouse-hook thread and message loop for actual left/right/middle clicks. Samples contain `t`, `x`, `y`, `visible`, `click`, and `shape` (`arrow`, `hand`, `ibeam`). The final JSON is an array, timestamps are monotonic seconds on the video timeline, and coordinates are normalized to the captured output. Click positions outside the recorded frame are marked invisible. Optional `FRAMEFLOW_CAPTURE_INPUT_DIAGNOSTICS=1` measures aggregate hook arrival/processing latency and writes one stop record; `FRAMEFLOW_CAPTURE_MOUSE_HOOK=off` is a comparison-only override that preserves position sampling but omits click markers. Neither override is enabled by default. See [input latency diagnostics](INPUT-LATENCY-DIAGNOSTICS.md).

System output and default microphone are separate WASAPI endpoints, each serviced by a dedicated background thread with bounded packet draining and cancellation. Hardware QPC packet timestamps are mapped to the cursor's monotonic clock; implausible driver timestamps fall back to callback time and are logged. Gaps are filled with silence and clock differences are corrected. Empty microphone streams are detected and reported. The video origin is estimated at its first delivered frame, so initial alignment still has capture/encoder scheduling latency. ScreenRecorderLib's frame event timestamp is callback time, not the underlying WGC frame PTS. The requested 30/60 fps is a capture target; variable input timestamps and software encoding preserve frame timing when frames are repeated or dropped.

The encoded MP4 duration is read from its sample timing. A static/slow source can stop before another unchanged video frame is submitted. If the positive difference between recording elapsed time and MP4 duration fits entirely within the observed last-frame-to-stop gap (plus one target frame of tolerance), the helper extends only the presentation duration and reports `tailHold`. The MP4 bytes/timestamps stay unchanged. Cursor and audio are aligned to presentation duration; preview/export must hold the last decoded image for that tail while continuing cursor/audio/camera playback. Missing time before the last delivered frame is never filled this way. Remaining elapsed/presentation discrepancies above 250 ms and 1% emit a warning. No whole-video stretching is performed.

Very sparse updates can also delay the first frame, so the estimated UTC origin may differ from the encoder's initial media clock. For example, a dedicated window updating every two seconds produced 8.767 seconds of MP4 during 8.130 seconds measured from the estimated origin. This negative difference cannot be explained by a missing tail: `tailHold` remains zero and a warning is preserved. Exact source-frame synchronization needs WGC `SystemRelativeTime` exposure in a future capture implementation. Long-duration physical lip-sync and performance checks remain release validation requirements.

## Files and recovery

Video is written as fragmented MP4 directly to disk; frames never accumulate in managed memory. WAV audio and `cursor.recovery.jsonl` are also streamed and flushed while recording. A recovery manifest records the common clock origin. On successful finalization the helper streams the aligned tracks, writes `recording.json`, then removes intermediate journals. On failure the journals remain; the desktop project library recovers readable recordings without a project manifest and preserves original files. A hard process kill or full disk can still lose the unflushed tail.

WAV has a 4 GB per-track limit. The helper disables that audio track with a warning and preserves the video instead of corrupting it. Final audio alignment temporarily needs space for both the original and aligned WAV. Protected video, secure desktops/UAC, exclusive fullscreen games, minimized windows, remote desktops, and unusual graphics/audio drivers need separate compatibility testing. Display capture records one chosen monitor, not a stitched multi-monitor canvas.

`capture.log` is an append-only JSON Lines diagnostic with lifecycle stages, dimensions, audio format and packet counts, first/last-frame callbacks, recording status timestamps, stop elapsed time, encoded duration differences, warnings, exception stack traces and HRESULTs. It never logs screen pixels or audio samples. Recorder warnings go to `encoder-hardware.log` / `encoder-software.log` when present. Recovery journals are retained whenever warnings or failures occur. Each cleanup stage is independent so one failed audio driver cannot prevent the video from being finalized. Start and stop share a lifecycle lock; stdin EOF also cancels startup instead of waiting for its timeout.

For controlled timeline investigation, `FRAMEFLOW_CAPTURE_SAMPLE_DIAGNOSTICS=1` adds fixed-size input PTS/duration and WriteSample wait statistics to the encoder log once at finalization. It is off by default and leaves the existing writes, sample properties, flush policy and encoder settings unchanged. See [video sample diagnostics](VIDEO-SAMPLE-DIAGNOSTICS.md) for fields, pure tests and limits of the evidence.

## Verification

Confirmed hardware encoder output restores exact source durations before fragmented MP4 muxing. `FRAMEFLOW_CAPTURE_ENCODED_TIMING=0` explicitly disables this safeguard for diagnostics; ordinary software recordings bypass it. The application's encoder preference is a separate policy. The repair does not change the original queue or flush strategy. See [encoded duration repair](ENCODED-SAMPLE-TIMING.md) for matching, native clock correlation, startup fallback, finalization error propagation and tests.
